# 协议计时：客户端、服务端与残余

2026-10-13/14历史实验摘要。专用客户端以64k历史、引擎同类协议请求访问原CUDA服务，诊断热修记录服务端阶段时间。该客户端、服务和完整日志未打包；本包保留[逐操作记录](../data/blackbox-session-05-ops.json)与[统计结果](../data/blackbox-session-05-analysis.json)。

## 已测数据

session-05共130个joined操作，去掉预先定义的前5个后，125个稳态操作：

| 时间窗口 | p50 | p95 |
| --- | ---: | ---: |
| Mac客户端发送至收完 | 4.098ms | 4.415ms |
| 服务端接收完成至发送完成 | 3.227ms | 3.443ms |
| 服务端dispatch | 2.830ms | 3.048ms |
| CUDA kernel event | 2.286ms | 2.459ms |
| 服务端egress | 0.380ms | 0.401ms |
| 成对“传输＋客户端残余” | 0.867ms | 1.040ms |

发布副本已用原request ID完成一对一join，再去除请求/进程/预约标识和绝对时钟，保留130条相对持续时间。[离线复算工具](../tools/check_blackbox.py)可重新得到全部14个统计值；运行 `python3 tools/check_blackbox.py`。p50采用median、p95采用nearest-rank，保留三位小数；这套复算完全匹配原摘要，但未找回原分析脚本，不能据此断言其内部实现。

各行统计量有包含关系，不能相加。残余由成对操作的持续时间差统计得到，也不等于两个p50简单相减。两机时钟起点不同，不能跨机直接相减原始时间戳。

## 能支持什么结论

这个专用客户端在该次负载下实现了约4.1ms的往返，没有重现早期引擎运行中约9–20ms的往返增长。协议和服务在至少这一种客户端/负载条件下可以更快，值得继续检查原引擎的成帧、复制、等待和调度。

**0.867ms必须称“传输＋客户端残余”。** 它包含未被服务端窗口覆盖的传输、客户端处理、调度与测量边界差异，不能称纯网线RTT或单独的网络吞吐。

原引擎某组RPC中位约10.05ms与本客户端4.098ms相差约6ms。这是跨客户端、跨运行条件的差异，不是同一运行中已隔离出的引擎内部时间。硬件热状态、并发、队列、数据路径和请求组织可能不同；只有匹配负载和受控干预才能确定因果。现有数据不能排除网络/服务在另一负载下的影响，也不能证明整段decoder迁移的通信成本。

## 失败与可复现边界

研究经历过客户端缺陷、前次未终结状态拒绝、响应校验不兼容和版本同步错误。历史记录保留了这些失败；成功session-05不能把此前失败改写成通过。

诊断热修在原研究中恢复，资源按原流程审查；这些是历史操作总结，不是本包提供的部署、恢复或清理工具。发布副本已移除旧nonce、进程号和回执；历史清理结论不能当新运行授权。

后续可用同输入、同服务、相同温度/并发条件比较客户端，分别报告本机持续时间，再定位成帧/复制/等待。完整原实验不能仅凭本包复现，见[复现说明](reproducibility.md)。
